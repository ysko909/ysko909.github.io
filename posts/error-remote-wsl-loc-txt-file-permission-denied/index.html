WSL環境でVSCode実行時に「remote-wsl-loc.txt: Permission denied」が発生した場合の対処法

Posted at — Nov 25, 2026

はじめに

WSL（Windows Subsystem for Linux）環境で開発を行っていると、Visual Studio Code（VS Code）の Remote - WSL 機能を利用する方が多いと思います。

ところがどっこい、ある日突然 code . コマンドが動作しなくなり、remote-wsl-loc.txt: Permission deniedのようなエラーに遭遇することがあります。本記事では、このエラーの原因と対処方法についてまとめます。誰かの役に立てば幸いです。こんなしょうもないエラーで時間を浪費するのは自分だけで良い・・・＿(　_´ω`)_ﾍﾟｼｮ

発生した事象

簡単に状況を書くと、WSL上で以下のコマンドを実行した際にエラーが発生しました。

code .

通常はVS Codeが起動し、カレントディレクトリが開かれるはずですが、今回は起動せずエラーで終了してしまいました。実際に表示されたエラーメッセージは次の通りです。

$ code .

/mnt/c/Users/hoge/AppData/Local/Programs/Microsoft VS Code/bin/code: 47: cannot create /tmp/remote-wsl-loc.txt: Permission denied
/mnt/c/Users/hoge/AppData/Local/Programs/Microsoft VS Code/bin/code: 53: /mnt/c/Users/hoge/.vscode/extensions/ms-vscode-remote.remote-wsl-0.104.3/scripts/wslCode.sh: not found

このエラーメッセージのポイントは以下の2点です。

  • /tmp/remote-wsl-loc.txt に書き込めない
  • wslCode.sh が見つからない

特に最初の

cannot create /tmp/remote-wsl-loc.txt: Permission denied

が根本原因になっているケースが多いようです。ということは、このファイルをどうにかすればいいわけです。

原因

調査したところ、VS Codeの Remote - WSL 拡張機能が利用する

/tmp/remote-wsl-loc.txt

というファイルの権限問題で発生することがあるようです。

具体的には、

  • 複数のWSLユーザーを利用している
  • 過去に別ユーザーでVS Codeを起動した
  • その際に作成された remote-wsl-loc.txt の所有者が別ユーザーになっている

といったケースで、現在ログインしているユーザーが当該ファイルへ書き込めなくなります。

Linuxの /tmp ディレクトリ自体は共有領域であるため、このような問題が発生する可能性があります。マジかよ。

対処方法①：ファイルを削除する（推奨）

もっとも手軽かつ早い対処方法です。

WSL上で以下を実行します。

sudo rm -f /tmp/remote-wsl-loc.txt

その後、再度VS Codeを起動します。

code .

多くの場合、これだけで復旧します。

対処方法②：ファイルの所有者を変更する

何らかの理由でファイルを残したい場合は、所有者を現在のユーザーへ変更します。

sudo chown your_username:your_username /tmp/remote-wsl-loc.txt

例：

sudo chown fuga:fuga /tmp/remote-wsl-loc.txt

このコマンド実行後に、

code .

で動作確認を行います。

対処方法③：使用する一時ファイルの場所を変更する

複数ユーザーでWSLを利用している場合、同じ問題が再発することがあります。この場合の回避策として、VS Codeの起動スクリプトを修正する方法があります。

対象ファイル：

%LocalAppData%\Programs\Microsoft VS Code\bin\code

このファイル内の

/tmp/remote-wsl-loc.txt

を

~/remote-wsl-loc.txt

へ置換します。

つまり、共有領域である /tmp ではなく、ユーザーごとのホームディレクトリを利用するよう変更します。ただ、ここまでの対処をしないといけないケースは、まあまあ稀だと思います。

注意点

この対策は、VS Code本体やRemote - WSL拡張機能のアップデート時に上書きされる可能性があります。

そのため、

  • 恒久対策ではない
  • 更新後に再設定が必要になる場合がある

という点には注意してください。

対処方法④：VS Code Serverを再構築する

権限問題を解消してもエラーが続く場合は、WSL側のVS Code Serverが壊れている可能性があります。

以下を実行して一度削除します。

rm -rf ~/.vscode-server

その後、

code .

を実行すると、自動的にVS Code Serverが再インストールされます。ただし、ここまで実施することは稀で、大体これまでの対策で回復すると思います。

切り分けのポイント

まずは以下を確認しましょう。

/tmp/remote-wsl-loc.txt の所有者確認

ls -l /tmp/remote-wsl-loc.txt

出力例：

-rw-r--r-- 1 anotheruser anotheruser 123 Nov 25 10:00 remote-wsl-loc.txt

現在のログインユーザーと所有者が異なる場合、今回の事象である可能性が高いです。

/tmp の権限確認

ls -ld /tmp

正常な環境では以下のようになっているはずです。

drwxrwxrwt

最後の t（Sticky Bit）が付与されていることが重要です。

まとめ

WSL環境で code . 実行時に以下のエラーが発生した場合、

cannot create /tmp/remote-wsl-loc.txt: Permission denied

多くの場合は /tmp/remote-wsl-loc.txt の権限問題が原因です。

まずは次の手順を試すことをおすすめします。

  1. sudo rm -f /tmp/remote-wsl-loc.txt
  2. code . を再実行
  3. 改善しない場合は ~/.vscode-server を削除
  4. 複数ユーザー環境では起動スクリプト修正も検討

WSLではWindowsとLinuxの権限管理が混在するため、一見するとVS Codeの不具合に見えても、実際にはLinux側のファイル所有権が原因であるケースが少なくありません。同様のエラーに遭遇した場合は、まず /tmp/remote-wsl-loc.txt の状態を確認してみるとよいかと思います。
